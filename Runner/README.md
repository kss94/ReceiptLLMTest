# Runner

프롬프트를 **점수**로 다루는 도구. 벤더가 늘어날 때 프롬프트를 벤더마다 손으로 튜닝하지
않으려고 만들었다.

```
runner run      --vendor <이름>   프롬프트 하나를 전체 케이스에 돌려 점수를 낸다
runner optimize --vendor <이름>   실패를 모델에 보여주고 절 하나씩 고쳐가며 점수를 올린다
```

키는 `Common/ApiKey.cs`에 박혀 있다. `runner`만 치면 전체 옵션이 나온다.

```bash
dotnet run --project Runner -- run --vendor Starbucks --repeat 2
```

지금 있는 벤더는 `Starbucks`(22건), `Megacoffee`(10건), `Baemin`(5건)이다.

## 왜 점수인가

`xUnit`의 합/불로는 "17개 필드 틀림"과 "1개 필드 틀림"이 똑같이 빨간 줄 하나다.
프롬프트를 고쳤을 때 나아졌는지 나빠졌는지 알 수 없다.

`ReceiptDiff.Report.Score`는 잎(스칼라 필드) 단위 정확도다. 정답의 필드 하나가 1점이고,
비교조차 못 한 필드와 정답에 없는데 나온 필드는 오답으로 센다.

- `score` — 케이스별 점수의 평균. 영수증 하나를 한 문제로 본다. **후보 비교의 기준값**
- `fieldScore` — 필드 수로 가중한 평균. 필드가 많은 영수증이 더 큰 비중을 갖는다

## 노이즈부터 알고 시작해라

추출 호출의 temperature는 고정이 아니다. **같은 프롬프트로 같은 케이스를 두 번 돌리면
점수가 다르게 나온다.**

실측(Starbucks): 22케이스를 `--repeat 1`로 돌리면 통과하던 케이스가 무작위로 하나씩 깨진다.
그 케이스만 3회씩 다시 돌리면 양쪽 프롬프트 모두 3/3 통과했다. 회귀가 아니라 노이즈였다.

그래서:

- 점수를 비교할 거면 `--repeat 2` 이상을 쓴다
- `maxSpread`(결과 JSON)보다 작은 점수 차이는 **읽지 마라**. 개선인지 알 수 없다
- 케이스 하나가 깨졌다고 바로 프롬프트를 고치지 말고, 그 케이스만 `--repeat 3`으로 확인해라

## 무엇이 어디에 남는가

`--out`을 주지 않으면 `Runs/<벤더>/<시각>/`이다. `Runs/`는 git에 올라가지 않는다.

```
<out>/<id>.actual.json   모델 응답 원본
<out>/<id>.diff.txt      차이. 차이가 없으면 파일을 지운다
<out>/result.json        점수 전체 (run은 같은 내용을 표준출력으로도 낸다)
```

`--repeat`이 2 이상이면 **가장 나쁜 시도**를 남긴다. 볼 것은 잘 된 쪽이 아니라 깨진 쪽이다.
표준출력은 결과 JSON, 표준오류는 사람이 읽는 진행 상황이다.

```bash
dotnet run --project Runner -- run --vendor Starbucks > result.json
```

## optimize가 하는 일

손으로 고칠 때와 다른 점은 **채택 조건** 하나뿐이다.

```
1. 현재 프롬프트로 전체 채점            → 기준선 (iter-00/)
2. 실패한 케이스의 차이·응답을 모델에 보여준다   (--show N건, 기본 3)
3. 모델이 절 하나를 골라 다시 쓴다      → 후보
4. 후보로 전체 다시 채점                 (iter-NN/)
5. 점수가 threshold보다 올랐을 때만 채택. 아니면 버린다
```

한 케이스를 고치려다 다른 케이스를 깨뜨리면 전체 점수가 내려가므로 자동으로 버려진다.
이게 손으로 할 때 놓치는 부분이다. 전부 통과하면 시도를 남겨 두고 멈춘다.

수정안을 내는 모델은 `--proposer`로 따로 고른다. 기본값은 뽑는 모델과 같지만 더 좋은 것을
쓰는 편이 낫다. 이쪽만은 설정이 고정이 아니라 thinking도 막지 않는다.

### 절 단위로만 고친다

36KB 프롬프트를 통째로 다시 쓰게 하면 고치라고 하지 않은 490줄까지 흔들린다.
그래서 모델에게는 `■`로 시작하는 **절 하나**만 돌려받고, 갈아끼우는 일은
`Common/PromptDocument`가 한다. 안전장치:

- 목록에 없는 절 제목이면 버린다
- 원래 절 길이의 30%도 안 되면 잘려 온 것으로 보고 버린다
- 갈아끼운 뒤 절 개수가 달라졌으면 버린다

반대로 모델이 제목의 `■`를 빠뜨리거나 제목 줄을 통째로 생략한 경우는 버리지 않고 받아낸다.
실측으로 5회 중 3회가 그 실수였다. 멀쩡한 수정안을 형식 때문에 버리면 시도 한 번이 날아간다.

제안 프롬프트에는 "특정 영수증의 값을 적지 말고 일반 규칙으로 적어라"가 들어 있다.
그래도 과적합이 완전히 막히지는 않는다. 아래를 봐라.

### `■`가 없는 벤더는 optimize를 못 쓴다

`■` 절은 지켜야 하는 규약이 아니라 optimize를 절 단위로 돌리기 위한 장치다.
지금 절이 있는 프롬프트는 Starbucks(14개)뿐이고, Megacoffee와 Baemin에는 하나도 없다.
절이 없으면 모델이 고칠 자리를 고르지 못하므로 그 벤더는 `run`으로 점수만 재고
프롬프트는 직접 고친다.

### 원본은 덮어쓰지 않는다

결과는 `<out>/SystemPrompt.txt`에만 쓴다. 확인하고 직접 복사해라.

```bash
diff LLMTests/Starbucks/SystemPrompt.txt Runs/<실행>/SystemPrompt.txt
```

`<out>/history.json`에 시도마다 무엇을 왜 고쳤고 점수가 어떻게 됐는지 남는다.

## 과적합 주의

`--cases`로 일부만 주고 optimize를 돌리면 그 케이스에만 맞는 규칙이 나올 수 있다.
**반드시 전체 케이스로 다시 채점해서 확인해라.**

실측 예: 실패 2건 + 통과 2건, 총 4케이스로 1회 돌렸더니 4/4가 됐다.
전체 22케이스로 검증하니 0.9755 → 0.9981 (20/22 → 21/22)로 실제로 올랐다.
추가된 건 4번 절의 규칙 한 줄이었다. 이번엔 잘 됐지만, 검증 없이는 알 수 없었다.

## 벤더 추가

Runner는 코드를 고치지 않는다. 폴더만 만들면 `--vendor <이름>`으로 돌아간다.

```
LLMTests/<벤더>/
  SystemPrompt.txt       규칙서
  UserPrompt.txt         JSON 형식
  <id>/answer.json       정답. 이 파일이 있는 폴더만 채점 대상이다
  <id>/*.jpg
```

파일 이름은 벤더가 달라도 이 두 개로 고정이다. 벤더 이름은 폴더가 나타낸다.
다른 파일로 채점하고 싶으면 `--system`, `--user`로 경로를 직접 준다.
벤더 폴더들의 상위는 `--root`로 바꾼다. 기본값은 소스의 `LLMTests/`다.

xUnit으로도 돌리려면 거기만 한 번 손댄다. `ReceiptTests`의 벤더 메서드를 복사해
벤더 이름이 들어간 두 군데(`[MemberData]`와 `RunCase`)를 바꾸면 케이스가 붙는다.
케이스 목록은 케이스 폴더에서 읽으므로 `[InlineData]`를 적을 필요가 없다.

> 프롬프트는 **벤더마다 따로 둔다.** 겹쳐 보이는 규칙(JSON 스키마, 공통 원칙)이 있어도
> 공통 프롬프트로 빼지 않는다. 벤더가 늘어나도 서로의 프롬프트를 건드리지 않는다.
